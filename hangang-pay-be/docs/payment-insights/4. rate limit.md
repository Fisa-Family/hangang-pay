# 4. rate limit

Rate Limit은 서버가 클라이언트 요청 수를 단위 시간 기준으로 제한하는 장치다.

결제 시스템에서 Rate Limit을 두는 이유는 두 가지다.

```
1. 짧은 시간에 반복되는 요청을 줄인다.
2. 서버와 Bank 서버를 갑자기 몰리는 트래픽으로부터 보호한다.
```

다만 Rate Limit은 중복 결제 방지의 최종 수단이 아니다.

중복 결제 방지는 멱등키와 DB unique, Bank 서버 멱등성이 담당해야 한다.
Rate Limit은 그 앞에서 요청을 줄여주는 역할이다.

## 1. Rate Limit이 막는 것과 못 막는 것

Rate Limit은 짧은 시간 안에 반복되는 요청을 제한한다.

```
같은 사용자가 10분 안에 결제 요청 20번
→ 제한

같은 IP에서 QR 조회 1분 안에 100번
→ 제한
```

하지만 Rate Limit만으로 중복 결제를 막을 수는 없다.

예를 들어 10분에 5번까지 허용한다고 해보자.
그럼 같은 결제 요청이 2번 들어오는 건 여전히 허용 범위 안이다.

```
중복 결제 방지
→ 멱등키 + DB unique + Bank 서버 unique

반복 요청 완화
→ Rate Limit
```

역할이 다르다.

그래서 결제 시스템에서는 둘 다 필요하다.

---

## 2. 제한 키를 어디서 잡을 것인가

Rate Limit은 어떤 키로 제한할지가 중요하다.

```
IP 기준
userId 기준
merchantId 기준
endpoint 기준
transactionUuid 기준
```

키에 따라 적용 위치도 달라진다.

| 기준 | 어디서 알 수 있는가 | 용도 |
| --- | --- | --- |
| IP | Gateway / Application | 비정상 트래픽 1차 차단 |
| userId / partyId | Application | 로그인 사용자 기준 제한 |
| merchantId | Application | 특정 가맹점 대상 과도한 요청 제한 |
| transactionUuid | Application | 같은 결제 실행 요청 반복 제한 |

Gateway에서는 보통 IP는 알 수 있지만, 세션 기반 `partyId`는 알기 어렵다.

우리 서비스는 세션 인증을 쓰고 있으므로, `partyId` 기준 제한은 Application 레벨에서 처리하는 게 자연스럽다.

---

## 3. Fixed Window


Fixed Window는 가장 단순하다.

```
1분 단위 창을 만든다.
현재 창에서 요청 수를 센다.
한도를 넘으면 거절한다.
```

예:

```
Window: 1분
Capacity: 10
```

장점:

- 구현이 쉽다.
- 메모리 사용량이 작다.

단점:

- 경계 구간 버스트 문제가 있다.

예를 들어:

```
00:59에 10번 요청
01:00에 10번 요청
```

실제로는 1초 사이에 20번 요청이 통과한다.

결제 API에는 이 문제가 별로 좋지 않다.

---

## 4. Sliding Window Counter


Sliding Window Counter는 Fixed Window의 경계 문제를 완화한다.

현재 창과 직전 창의 카운터를 가중 평균해서 현재 요청량을 추정한다.

```
추정 요청 수 = 현재 창 카운트 + (직전 창 카운트 × 겹치는 비율)
```

장점:

- Fixed Window보다 경계 버스트에 강하다.
- 메모리 사용량이 작다.

단점:

- 정확한 요청 로그를 모두 저장하는 방식은 아니다.
- 근사값이다.

정확도가 어느 정도 필요하지만, 메모리도 아껴야 한다면 괜찮다.

---

## 5. Sliding Window Logging


Sliding Window Logging은 현재 시각 기준 최근 N분 안의 요청 타임스탬프를 모두 저장한다.

Redis로 구현하면 보통 Sorted Set을 쓴다.

```
KEY: rate:payment:{partyId}:{ip}

ZADD
→ 현재 타임스탬프 삽입

ZREMRANGEBYSCORE
→ 윈도우 밖 요청 제거

ZCARD
→ 현재 요청 수 확인
```

장점:

- 정확도가 가장 높다.
- Fixed Window의 경계 버스트 문제가 없다.

단점:

- 요청 수에 비례해서 저장 공간이 증가한다.
- 요청마다 만료 타임스탬프 정리 연산이 발생한다.

결제처럼 정확도가 중요한 API에는 잘 맞는다.

다만 모든 API에 이걸 쓰면 부담이 크다.
정말 필요한 곳에만 쓰는 게 좋다.

---

## 6. Token Bucket


Token Bucket은 버킷에 토큰을 일정 속도로 채워두고, 요청마다 토큰을 하나씩 소비하는 방식이다.

```
rate: 초당 1개 충전
burst: 최대 10개 저장
```

요청이 들어왔을 때 토큰이 있으면 통과한다.
없으면 거절한다.

장점:

- 순간적인 트래픽 스파이크를 어느 정도 허용할 수 있다.
- 평균 처리율을 일정하게 유지할 수 있다.
- Gateway나 Application 앞단에서 서버 보호용으로 좋다.

단점:

- 튜닝을 잘못하면 burst를 너무 많이 허용할 수 있다.
- “최근 N분에 정확히 몇 번” 같은 정책에는 Sliding Window보다 덜 직관적이다.

Bucket4j를 쓰면 구현이 편하다.
Redis와 붙이면 멀티 WAS에서도 사용할 수 있다.

---

## 7. 결제 API에서는 어떻게 조합할 것인가

정확도와 스파이크 대응을 둘 다 잡고 싶다면 둘을 섞는 게 맞다.

다만 순서가 중요하다.

내 기준으로는 아래 순서가 더 자연스럽다.

```
1차: Token Bucket
→ 서버 보호
→ 큰 스파이크 먼저 흡수

2차: Sliding Window Logging / Counter
→ 결제 업무 한도 정확히 제한
→ userId + IP + merchantId 기준 정책 적용

3차: Bank outbound Token Bucket
→ Bank 서버로 나가는 호출량 보호
```

#### **왜 Token Bucket을 앞에 두는가?**

Sliding Window Logging은 요청마다 **`Redis** **ZSET**` 연산이 들어간다.
가장 앞단에서 모든 스파이크 요청에 이 연산을 수행하면 부담이 커질 수 있다.

그래서 앞에서는 비교적 싼 Token Bucket으로 큰 트래픽을 먼저 줄이고,
실제 결제 정책은 뒤에서 Sliding Window로 정확하게 판단하는 게 낫다.

단, Gateway가 없고 Application에서만 구현한다면 처음부터 Sliding Window를 결제 API에 직접 붙여도 된다.
규모가 작을 때는 단순한 게 더 낫다.

## 8. 우리 서비스 적용안

현재 서비스 기준으로는 아래 정도가 현실적이다.

### QR 가맹점 조회 API

```
GET /api/v1/merchant/{merchantId}
```

목적:

```
QR 반복 스캔 / 비정상 조회 방지
```

추천:

```
rate:qr:{ip}
rate:qr:{partyId}
1분에 10회
```

다만 현재 컨트롤러가 세션 값을 받지 않는다면 `partyId` 기준 제한은 바로 적용하기 어렵다.
그 경우에는 먼저 IP 기준으로 시작하고, 필요하면 세션 기반으로 확장한다.

### 결제 실행 API

```
POST /api/v1/payment/execute
```

목적:

```
결제 버튼 반복 클릭
같은 사용자 단시간 결제 남용
Bank 서버 호출량 보호
```

추천:

```
Token Bucket:
rate:payment:burst:{partyId}
짧은 순간 스파이크 완화

Sliding Window Logging:
rate:payment:window:{partyId}:{ip}
10분에 5회

Bank outbound Token Bucket:
rate:bank:payment
Bank 서버 전체 보호
```

여기서 **`transactionUuid`** 중복은 Rate Limit이 아니라 멱등성에서 처리한다.

```
transactionUuid 중복
→ 기존 응답 재전달 or PROCESSING 반환

partyId 기준 과도한 결제 시도
→ Rate Limit
```

### 실패 결제 방어

나중에 카드나 외부 PG가 붙는다면 실패 결제 방어도 필요하다.

예:

```
동일 user가 1시간 내 실패 10회
동일 IP에서 서로 다른 카드 20개 시도
동일 merchant에 비정상 결제 시도 급증
```

현재 서비스에서는 카드 fingerprint 같은 값이 없으므로 우선순위는 낮다.

---

## 9. 최종 결론

Rate Limit은 중복 결제를 막는 핵심 장치가 아니다.

핵심 장치는 멱등성이다.

Rate Limit은 그 앞에서 요청량을 줄이고, 서버와 Bank 서버를 보호한다.

우리 서비스의 결론은 이렇다.

```
QR 조회
→ IP 또는 partyId 기준 제한

결제 실행
→ Token Bucket으로 스파이크 완화
→ Sliding Window로 업무 한도 정확히 제한
→ Bank outbound 제한으로 Bank 서버 보호

중복 결제
→ 멱등키 + DB unique + Bank 서버 unique로 해결
```

처음부터 너무 복잡하게 갈 필요는 없다.

1차 구현은 아래 정도면 충분하다.

```
결제 실행: partyId 기준 Sliding Window
Bank outbound: 간단한 Token Bucket
QR 조회: IP 기준 제한
```

트래픽이 실제로 커지면 그때 Gateway 레벨 Token Bucket과 더 세밀한 키를 추가하면 된다.
