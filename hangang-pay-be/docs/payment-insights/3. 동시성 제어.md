# 3. 동시성 제어

동시성 제어는 결제에서 정말 중요하다.

이유는 간단하다.

**두 요청이 동시에 같은 자원을 건드리면, 서버 코드가 맞아도 결과가 틀릴 수 있기 때문이다.**

특히 결제에서는 “따닥” 문제가 생긴다.

```
사용자가 결제 버튼을 빠르게 2번 누름
→ 두 요청이 거의 동시에 들어옴
→ 둘 다 같은 지갑 잔액을 보고 가능하다고 판단
→ 둘 다 Bank 서버에 결제 요청
→ 중복 결제 가능
```

이건 단순히 프론트에서 버튼 비활성화를 한다고 해결되는 문제가 아니다.
서버에서 막아야 한다.

## 1. 동시성 문제가 생기는 이유

동시성 문제는 보통 아래 구간에서 발생한다.

```
조회
→ 판단
→ 저장
```

예를 들어:

```
1번 요청: 기존 PENDING 없음 확인
2번 요청: 기존 PENDING 없음 확인
1번 요청: PENDING 생성
2번 요청: PENDING 생성
```

둘 다 “없다”고 판단했기 때문에 둘 다 생성한다.

이 사이를 임계 구역이라고 볼 수 있다.


```
L (Lock)   : 임계 구역 진입
U (Unlock) : 임계 구역 종료
S (Store)  : 저장
```

`L ~ S` 사이에 다른 요청이 들어오면 중복이 생긴다.

그래서 공유 자원을 기준으로 락을 잡거나, DB 제약조건으로 마지막에 막아야 한다.

## 2. DB Unique Constraint

유니크 제약조건이라고 부르지만, MySQL InnoDB에서는 사실상 유니크 인덱스로 동작한다.

```sql
CREATE TABLE transaction (
    transaction_uuid VARCHAR(36) NOT NULL,
    UNIQUE KEY uk_transaction_uuid (transaction_uuid)
);
```

혹은:

```sql
ALTER TABLE transaction
ADD CONSTRAINT uk_transaction_uuid UNIQUE (transaction_uuid);
```

결제에서는 유니크 인덱스가 꼭 필요하다.

예를 들어 **`transactionUuid`**가 같으면 같은 결제 실행 요청이다.
이 값이 DB에서 중복 저장되면 안 된다.

```
Redis 락 성공
→ 처리 중 서버 장애
→ Redis TTL 만료
→ 같은 요청 재시도
```

이런 상황에서도 DB unique는 마지막 방어선이 된다.

## 3. 유니크 인덱스의 비용

유니크 인덱스는 공짜가 아니다.

`INSERT`, `UPDATE`를 할 때마다 중복 여부를 확인해야 한다.

```
새 row 저장
→ 유니크 인덱스에서 같은 값이 있는지 확인
→ 없으면 저장
→ 있으면 에러
```

일반 보조 인덱스보다 쓰기 비용이 더 크다.

InnoDB의 Change Buffer 최적화도 유니크 인덱스에는 적용하기 어렵다.

Change Buffer는 대충 이런 개념이다.

```
지금 당장 보조 인덱스 페이지를 읽지 말고
변경 내용을 버퍼에 쌓아둔 다음
나중에 해당 페이지가 메모리에 올라오면 합친다.
```


그런데 유니크 인덱스는 저장 전에 중복 여부를 반드시 확인해야 한다.
**확인을 미루면 유니크 보장이 깨진다.**

그래서 유니크 인덱스는 쓰기 성능에 부담이 있다.

그럼에도 결제에서는 도입해야 한다.

> **속도가 조금 느린 건 괜찮지만, 결제가 두 번 발생하는 건 안 된다.**
>

## 4. 낙관적 락과 비관적 락

락은 크게 두 가지 방식으로 생각할 수 있다.

### 낙관적 락

충돌이 자주 나지 않을 거라고 보고, 저장 시점에 버전을 확인한다.

```sql
SELECT id, balance, version
FROM wallet
WHERE id = 1;

UPDATE wallet
SET balance = balance - 10000,
    version = version + 1
WHERE id = 1
  AND version = 1;
```

버전이 같으면 성공한다.
버전이 다르면 누군가 먼저 바꾼 것이므로 실패하고 재시도한다.

장점:

- 조회 시점에 락을 오래 잡지 않는다.
- 충돌이 적으면 성능이 좋다.

단점:

- 충돌이 많으면 재시도가 많아진다.
- 결제처럼 외부 API 호출이 끼면 재시도 설계가 어려워진다.

### 비관적 락

충돌이 날 거라고 보고, 읽는 순간부터 잠근다.

```sql
SELECT *
FROM transaction
WHERE transaction_uuid = ?
FOR UPDATE;
```

장점:

- 같은 row를 동시에 수정하지 못하게 막을 수 있다.
- DB 트랜잭션 안에서는 이해하기 쉽다.

단점:

- 락을 오래 잡으면 대기 요청이 늘어난다.
- 외부 API 호출을 트랜잭션 안에서 하면 위험하다.
- 데드락이 생길 수 있다.

---

## 5. 데드락 문제

데드락은 서로가 잡은 락을 기다리면서 아무도 진행하지 못하는 상태다.

예를 들어:

```
WAS1: A row lock 획득 → B row lock 대기
WAS2: B row lock 획득 → A row lock 대기
```

둘 다 서로를 기다린다.

결제에서는 지갑 2개가 자주 등장한다.

```
fromWallet
toWallet
```

만약 어떤 요청은 `fromWallet → toWallet` 순서로 잠그고,
다른 요청은 `toWallet → fromWallet` 순서로 잠그면 데드락 가능성이 생긴다.

그래서 DB 락을 쓴다면 락 획득 순서를 고정해야 한다.

```
항상 walletId 작은 순서로 잠근다
항상 partyId 작은 순서로 잠근다
```

이런 규칙이 없으면 비관적 락도 안전하지 않다.

## 6. 분산 락

멀티 WAS에서는 **`synchronized`**가 의미가 없다.

```
WAS1 JVM 안의 synchronized
→ WAS2 JVM은 모름
```

즉, 서버가 여러 대면 JVM 로컬 락은 중복 결제를 막지 못한다.

여러 WAS가 같이 볼 수 있는 자원에 락을 걸어야 한다.

이게 분산 락이다.

```
payment:lock:{partyId}
payment:lock:{transactionUuid}
wallet:lock:{walletId}
```

락 키는 무엇을 보호할지에 따라 달라진다.

| 락 키 | 보호 대상 |
| --- | --- |
| `payment:lock:{transactionUuid}` | 같은 **결제 실행 요청** 중복 |
| `payment:lock:{fromPartyId}` | 같은 **사용자의 동시 결제** |
| `wallet:lock:{walletId}` | 같은 **지갑의 동시 변경** |

결제 실행에서는 보통 `transactionUuid`와 `fromPartyId`를 같이 고려한다.

## 7. Redis Lettuce 스핀 락과 Redisson Pub/Sub

Redis로 락을 잡는 방법은 여러 가지가 있다.

### Lettuce 스핀 락


```
SET lockKey value NX PX 10000
```

락 획득에 실패하면 일정 시간 뒤 다시 시도한다.

```
락 획득 실패
→ 100ms 대기
→ 다시 시도
→ 실패하면 또 대기
```

구현은 단순하다.

하지만 트래픽이 많으면 락을 얻으려는 요청들이 계속 Redis를 두드린다.
**결제 요청이 몰리는 상황에서는 부담이 커진다.**

### Redisson Pub/Sub


Redisson은 락 해제를 기다리는 스레드가 계속 Redis를 때리는 방식이 아니다.

락이 해제되면 Pub/Sub으로 대기 중인 쪽에 알려준다.

```
Thread A 락 획득
Thread B 락 대기
Thread A 락 해제
Redis channel로 알림
Thread B 락 획득 시도
```

스핀 방식보다 부하가 적고, 분산 락 구현도 직접 짜는 것보다 안전하다.

그래서 우리 서비스에서는 Redisson을 쓰는 쪽이 낫다.

## 8. Caffeine은 왜 애매한가

Caffeine은 로컬 캐시다.

싱글 WAS에서는 빠르고 좋다.
하지만 멀티 WAS에서는 각 서버가 서로의 캐시를 모른다.

```
WAS1 Caffeine
WAS2 Caffeine
```

WAS1에 멱등키가 있어도 WAS2는 모른다.

동기화하려면 Redis Pub/Sub 같은 걸 붙여야 한다.

```
WAS1이 멱등키 저장
→ Redis Pub/Sub 발행
→ WAS2가 수신
→ WAS2 Caffeine 갱신
```

근데 여기까지 할 거면 그냥 Redis를 쓰는 게 낫다.

그래서 결제 멱등성이나 분산 락의 핵심 저장소로 Caffeine을 쓰는 건 맞지 않다.

## 9. 우리 서비스의 적용 전략

우리 서비스에서는 아래처럼 역할을 나누는 게 좋다.

### 1차: DB unique

```
transaction.transaction_uuid unique
bank_transaction.transaction_uuid unique
```

최종 방어선이다.
Redis가 실패해도 DB에서 중복 저장은 막아야 한다.

### 2차: Redis / Redisson 분산 락

```
payment:lock:{fromPartyId}
payment:lock:{transactionUuid}
```

동시 요청을 줄이고, 같은 사용자의 결제 실행이 꼬이지 않게 한다.

다만 외부 Bank 서버 호출을 DB 트랜잭션 안에서 오래 잡으면 안 된다.

권장 흐름은 이렇다.

```
1. 짧은 트랜잭션으로 PENDING 생성
2. 짧은 트랜잭션으로 PROCESSING 전환
3. DB 트랜잭션 밖에서 Bank 서버 호출
4. 별도 트랜잭션으로 SUCCESS / FAILED / UNKNOWN 반영
```

락도 너무 오래 잡으면 안 된다.
Bank 서버 응답이 느리면 `leaseTime`보다 호출 시간이 길어질 수 있기 때문이다.

### 3차: Bank 서버 멱등성

BE 서버에서 막는 것만으로는 부족하다.

Bank 서버도 `transactionUuid` unique를 가져야 한다.

```
BE 서버 중복 방어
+ Bank 서버 중복 방어
= 실제 중복 결제 방지
```

## 10. 최종 결론

동시성 제어는 하나의 기술로 끝나지 않는다.

결제에서는 여러 겹으로 막아야 한다.

```
프론트 버튼 비활성화
→ Rate Limit
→ Redis 분산 락
→ DB unique
→ Bank 서버 unique
```

각자의 역할이 다르다.

- 프론트는 UX 보완이다.
- Rate Limit은 짧은 시간의 반복 요청을 줄인다.
- 분산 락은 멀티 WAS 동시 실행을 줄인다.
- DB unique는 최종 중복 저장을 막는다.
- Bank 서버 unique는 실제 돈이 두 번 움직이는 것을 막는다.

결론은 이렇다.

> **결제 시스템에서는 Redis 락을 믿되, Redis 락만 믿으면 안 된다.**
>

마지막 방어선은 항상 DB unique와 Bank 서버의 멱등 처리여야 한다.
