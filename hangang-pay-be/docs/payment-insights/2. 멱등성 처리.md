# 2. 멱등성 처리

> **연산을 여러 번 적용하더라도 결과가 처음 한 번만 적용했을 때와 완전히 같은 성질**
>

멱등성은 결제 시스템에서 거의 필수다.

이유는 단순하다.

**같은 결제 요청이 여러 번 들어와도 실제 결제는 한 번만 실행되어야 하기 때문이다.**

사용자가 결제 버튼을 두 번 누를 수도 있고, 모바일 네트워크가 불안해서 앱이 같은 요청을 재전송할 수도 있다.
서버 입장에서는 이걸 모두 정상적으로 막아야 한다.

## 1. 어떤 문제가 생기는가

가장 단순한 문제는 이것이다.

```
사용자가 같은 QR을 동시에 2번 태그
→ 두 요청이 동시에 들어옴
→ 둘 다 PENDING 생성 시도
→ 중복 PENDING 생성
```

여기까지만 보면 그냥 화면 문제처럼 보인다.

하지만 실제로 더 위험한 건 결제 실행 요청이다.

```
사용자가 결제 버튼을 2번 누름
→ 두 요청이 동시에 들어옴
→ 둘 다 Bank 서버에 payment 요청
→ 중복 결제 발생 가능
```

QR 중복은 불편한 정도지만, Bank 서버 결제 중복은 돈이 두 번 움직이는 문제다.

그래서 멱등성은 단순한 UX 보완이 아니라 정합성 장치다.

---

## 2. QR 재태그와 결제 멱등성은 다르다

여기서 책임을 분리해야 한다.

```
QR 재태그 방지
→ 같은 결제 화면을 다시 보여주는 문제

결제 멱등성
→ Bank 서버에 같은 결제 실행이 두 번 나가지 않게 하는 문제
```

둘은 비슷해 보이지만 역할이 다르다.

QR을 다시 찍었다고 해서 항상 같은 결제 실행 요청은 아니다.
반대로 QR은 한 번만 찍었어도 결제 버튼을 여러 번 누르면 결제 실행 요청은 여러 번 나갈 수 있다.

그래서 `qr_uuid` 하나로 모든 걸 막으려고 하면 역할이 섞인다.

우리 서비스에서는 아래처럼 나누는 게 좋다.

| 값 | 역할 | 생성 주체 |
| --- | --- | --- |
| `merchantId` | 어떤 가맹점의 QR인지 식별 | 가맹점 등록 시 DB |
| `PENDING Transaction` | 사용자의 결제 의도 | 백엔드 |
| `transactionUuid` | 결제 실행 멱등키, Bank 서버에도 전달 | 백엔드 |

QR은 가맹점 식별까지만 담당하고, 결제 의도와 결제 실행 중복 방지는 `Transaction`이 담당한다.

---

## 3. 멱등키 하나만으로 판단하면 안 된다

현실적인 결제 API는 멱등키만 보지 않는다.

토스페이먼츠도 멱등키를 사용할 때 아래 조합으로 같은 요청인지 판단한다.

```
Idempotency-Key
+ API 키
+ API 주소
+ HTTP 메서드
```

즉, 같은 UUID라도 호출 주체나 API가 다르면 다른 요청이다.

우리 서비스도 최소한 아래 값을 같이 봐야 한다.

```
transactionUuid
+ endpoint
+ method
+ fromPartyId
+ merchantPartyId
+ amount
```

여기서 중요한 게 `requestHash`다.

```
첫 요청:
transactionUuid = A
amount = 10000
merchantPartyId = 10
→ requestHash = H1

두 번째 요청:
transactionUuid = A
amount = 20000
merchantPartyId = 10
→ requestHash = H2
```

같은 `transactionUuid`인데 요청 내용이 다르다면 그냥 중복 요청이 아니다.
이건 충돌이다.

이 경우에는 기존 응답을 재사용하면 안 되고, `IDEMPOTENCY_CONFLICT` 같은 에러로 막아야 한다.

---

## 4. 멱등키 보관시간과 결제 유효시간

헷갈리기 쉬운 부분이다.

```
결제 승인 유효시간
→ 이 결제를 언제까지 진행할 수 있는가

멱등키 보관시간
→ 같은 요청을 언제까지 중복으로 판단할 것인가
```

둘은 다르다.

예를 들어 결제 유효시간을 10분으로 잡을 수 있다.

```
PENDING 생성
→ 10분 동안 결제 가능
→ 10분 지나면 EXPIRED
```

하지만 멱등키 보관시간은 더 길 수 있다.

```
결제는 이미 끝남
→ 사용자가 같은 요청을 나중에 다시 보냄
→ 서버는 "이미 처리된 요청"이라고 판단해야 함
```

토스페이먼츠의 멱등키 유효기간이 15일인 이유도 이쪽에 가깝다.
15일 동안 결제를 승인할 수 있다는 뜻이 아니라, 15일 동안 같은 민감 요청의 중복 실행을 막고 기존 응답을 재현한다는 의미다.

우리 서비스는 이렇게 분리하는 게 낫다.

- **PENDING Transaction 유효시간:**
  - 10분
- **IdempotencyRecord 보관시간:**
  - 최소 24시간, 가능하면 7일 이상
- **UNKNOWN 추적 기간:**
  - Bank 서버 조회 가능 기간과 동일

## 5. Redis `SET NX`만으로 충분한가

> **`SET NX` : 존재하지 않을 때만 키를 저장**
>

처음 생각은 보통 이렇다.

```
Redis SET idempotency:{transactionUuid} 1 NX EX 600
→ 성공하면 처리
→ 실패하면 중복 요청 에러
```

이 방식은 원자성은 좋다.

`SET NX`는 확인과 저장이 한 번에 일어난다.

```
멱등키 확인
→ 없으면 저장
→ 처리
```

이 사이에 다른 요청이 끼어들 수 없다.

하지만 결제 API에서는 이것만으로 부족하다.

왜냐하면 멱등성의 목표는 단순히 **중복 요청을 에러로 막는 것**이 아니라, 가능하면 **첫 요청과 같은 응답을 돌려주는 것**이기 때문이다.

```
첫 요청 성공
→ 클라이언트가 응답을 못 받음
→ 같은 transactionUuid로 재시도
→ 서버는 기존 SUCCESS 응답을 다시 줘야 함
```

여기서 그냥 **`PAYMENT_DUPLICATE_REQUEST`**를 내려버리면 사용자는 결제가 됐는지 알 수 없다.

그래서 Redis 값이 `"1"`이면 부족하다.
최소한 상태와 결과를 저장해야 한다.

```json
{
  "requestHash": "abc...",
  "status": "SUCCESS",
  "transactionId": 123,
  "responseSnapshot": {
    "approvalNumber": "APV-2026-00000001",
    "status": "SUCCESS",
    "amount": 10000
  }
}
```

## 6. 우리 서비스의 멱등성 설계

우리 서비스에서는 DB와 Redis를 같이 쓰는 게 현실적이다.

Redis는 빠른 중복 요청 차단에 좋고, DB unique는 최종 방어선이다.

```
1. 요청 수신
2. transactionUuid + endpoint + method + request body로 requestHash 생성
3. Redis idempotency record 조회
4. 없으면 PROCESSING record 생성 시도
5. DB transaction_uuid unique로 최종 중복 방어
6. 처리 완료 후 Redis record에 responseSnapshot 저장
```

상태별 응답은 이렇게 간다.

| 기존 멱등 기록 | 처리 |
| --- | --- |
| 없음 | 새 요청으로 처리 |
| 같은 key + 같은 requestHash + 처리 중 | `PROCESSING` 또는 409 응답 |
| 같은 key + 같은 requestHash + 완료 | 기존 응답 재전달 |
| 같은 key + 다른 requestHash | `IDEMPOTENCY_CONFLICT` |

여기서 DB unique는 반드시 있어야 한다.

Redis는 장애가 날 수 있고, TTL 때문에 기록이 사라질 수 있다.
하지만 DB의 `transaction_uuid` unique는 실제 거래 중복 저장을 막는 마지막 방어선이다.

## 7. Bank 서버도 멱등해야 한다

가장 중요한 부분이다.

우리 BE 서버에서 멱등성을 아무리 잘 처리해도, Bank 서버에 같은 요청이 두 번 도착할 수 있다고 가정해야 한다.

예를 들어:

```
BE 서버가 Bank 서버에 payment 요청
→ Bank 서버가 결제 성공
→ 응답이 오기 전에 네트워크 타임아웃
→ BE 서버는 UNKNOWN 저장
→ 재시도 또는 폴러가 다시 확인
```

이때 Bank 서버가 `transactionUuid` 기준으로 멱등하지 않으면 중복 transfer가 발생할 수 있다.

Bank 서버는 최소한 아래 규칙을 가져야 한다.

```
POST /api/v1/transactions/payment

1. transactionUuid가 없으면 새 결제 처리
2. transactionUuid가 있고 requestHash도 같으면 기존 결과 반환
3. transactionUuid가 있는데 requestHash가 다르면 충돌 에러
4. 처리 중이면 PROCESSING 반환
```

그리고 조회 API도 필요하다.

```
GET /api/v1/transactions/{transactionUuid}
```

이 API가 있어야 `UNKNOWN` 상태를 복구할 수 있다.

---

## 8. 최종 결론

멱등성은 `SET NX` 하나로 끝나는 문제가 아니다.

결제에서 필요한 멱등성은 아래에 가깝다.

```
같은 요청이 여러 번 들어오면
→ 실제 실행은 한 번만 하고
→ 처리 중이면 처리 중이라고 말하고
→ 끝났으면 같은 응답을 다시 돌려주고
→ 같은 key에 다른 요청이면 충돌로 막는다
```

우리 서비스의 결론은 이렇다.

1. **`transactionUuid`**는 결제 실행 멱등키로 사용한다.
2. **`requestHash`**를 같이 저장해서 같은 요청인지 검증한다.
3. Redis에는 단순 **`"1"`**이 아니라 상태와 응답 스냅샷을 저장한다.
4. DB에는 **`transaction_uuid`** unique를 둬서 최종 중복을 막는다.
5. Bank 서버도 **`transactionUuid`** 기준으로 반드시 멱등해야 한다.

결제 시스템에서 제일 무서운 건 요청이 실패하는 게 아니다.

**실제로는 성공했는데 서버가 실패라고 믿고, 사용자가 다시 결제하게 만드는 것**이다.

멱등성은 바로 그 문제를 막기 위한 장치다.
